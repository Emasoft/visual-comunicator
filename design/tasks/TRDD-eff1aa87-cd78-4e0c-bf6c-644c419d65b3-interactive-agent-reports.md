## 1. Original user request (verbatim)

> i urgently need the ability to make the agents report becoming interactive,
> so i can answer/comment any issue the agents found and wrote in the report,
> reading the answer to each directly printed near the text of the description
> and right next to my comment.

## 2. Problem and goal

Today, agents (code-auditor, llm-externalizer, plugin-validator, etc.) write reports as plain Markdown files in `<repo>/reports/<component>/<timestamp>-<slug>.md`. The user reads those reports linearly. To dispute or follow up on a finding, they have to either:

- Manually pick a quote and paste it back into chat, or
- Track multiple findings across multiple rounds in their head.

The goal is to render an agent's report as an **interactive HTML page** where:

1. Each finding has its own anchored thread.
2. Below each finding the user can type a reply / question / correction.
3. The user submits all replies at once with the existing Submit button.
4. The orchestrator picks up the per-finding replies, generates a per-finding response, and re-renders the page so the new round of claude replies appears **inline next to the user's comment** (and the user's comment stays visible above it).
5. The user can keep adding rounds — every prior turn stays visible in chronological order, scoped per finding.

## 3. Design

### 3.1 Source format (what agents write)

Agents write a normal Markdown report with `## Finding N: <title>` headers. The body of each finding is everything from that header until the next `## ` header at the same level. Optional metadata goes in an HTML comment immediately after the header:

```markdown
# Code review report
*Generated by code-correctness-agent on 2026-05-06.*

## Finding 1: Null pointer in parser
<!-- ve-finding severity="major" file="src/parser.ts:42" -->

The function `parseInput` doesn't check for null before calling `.split(',')`.

```ts
function parseInput(s: string) {
  return s.split(',');  // ← throws on null
}
```

**Recommended fix:** add a null guard at the top.

## Finding 2: Missing error handling
<!-- ve-finding severity="minor" file="src/api.ts:88" -->

The fetch call has no `.catch()` …
```

`severity` and `file` are advisory — the renderer surfaces them in a chip below the finding header. Any other attribute on the comment becomes a `data-ve-finding-<key>` attribute on the section.

The user has to **stick to the convention** — `## Finding N:` heading + optional comment. The renderer will flag any heading that doesn't match the pattern as a structural warning at the top of the page so the agent can correct itself in the next iteration.

### 3.2 Renderer (what makes the HTML)

A python script `plugins/visual-explainer/scripts/render-interactive-report.py` takes:

- `--report <report.md>` — the agent's report
- `--replies <replies.json>` — optional, prior rounds (one entry per finding × round)
- `--out <report.html>` — where to write the interactive page

It emits an HTML page with:

- The plugin's themed CSS variables in the page `:root`.
- The full report rendered to HTML (markdown → HTML via `python -m markdown` or hand-written; minimal: just headings, paragraphs, code blocks, lists, links).
- Each finding wrapped in a `<section data-ve-finding-id="finding-N">`. The section structure:

```html
<section data-ve-finding-id="finding-1"
         data-ve-finding-severity="major"
         data-ve-finding-file="src/parser.ts:42">
  <h2>Finding 1: Null pointer in parser</h2>
  <div class="ve-finding-meta">
    <span class="ve-finding-chip ve-finding-chip--major">major</span>
    <span class="ve-finding-file"><code>src/parser.ts:42</code></span>
  </div>
  <div class="ve-finding-body">
    <!-- rendered markdown body -->
  </div>
  <div class="ve-finding-thread">
    <!-- prior rounds, oldest first -->
    <div class="ve-finding-round" data-round="1">
      <blockquote class="ve-user-comment">
        <div class="ve-finding-author">You · round 1</div>
        I'd rather use a default value than throw.
      </blockquote>
      <div class="ve-claude-reply">
        <div class="ve-finding-author">Claude · round 1</div>
        OK, defaulting `s` to <code>""</code> is fine — split returns
        a one-element array on an empty string.
      </div>
    </div>
    <!-- always-present new-reply textarea -->
    <textarea class="ve-finding-reply"
              data-ve-finding-reply
              data-ve-finding-id="finding-1"
              placeholder="Reply to this finding…"
              rows="3"></textarea>
  </div>
</section>
```

Above the article, the renderer also drops a small banner with the page's purpose and a "Submit (N)" reminder pointing at the existing fixed buttons.

The whole content is wrapped in `<article data-ve-prose>` so the multi-click + drag-text features (Phases 2–4) also work — a user can drag-select a phrase from the finding body to add it as evidence, on top of typing a reply in the textarea.

The rendered page links the runtime: `<script src="/path/to/ve-runtime.js"></script>`.

### 3.3 Runtime extension (what makes textareas selectable)

A new entry kind:

```json
{ "kind": "finding-reply", "findingId": "finding-1", "text": "I prefer to default to '' instead." }
```

- Each `<textarea data-ve-finding-reply data-ve-finding-id="…">` gets an `input` listener (debounced 350 ms).
- The listener pushes / updates a `finding-reply` entry keyed by `findingId` — replace-on-each-keystroke so only the latest text per finding is sent.
- Empty textarea (after trim) → entry is removed.
- `entryId` = `finding-reply:<findingId>` — guarantees one entry per finding regardless of how many keystrokes happen.
- The textarea itself is **not** wrapped by the global element-toggle handler; it's an editable form control and `isInteractiveControl()` already excludes it.

### 3.4 Submit / pickup

The user types replies in any number of finding threads, then clicks **Submit** (the existing top-right or bottom-left button) — exactly the same Submit/Exit flow as every other selection. The POST body includes `selections: [{kind:"finding-reply", findingId, text}, …]` alongside any other selections (e.g. a code line range from elsewhere on the page).

`scripts/ve-select.py` already writes the POST body to a known location (the `--out` path it was launched with). The orchestrator reads that JSON, generates per-finding responses, updates `<report>.replies.json` (a sidecar that mirrors the report path), and re-runs the renderer so the next iteration of the page shows the new round.

`<report>.replies.json` schema:

```json
{
  "rounds": 2,
  "findings": {
    "finding-1": [
      {"round": 1, "user": "I prefer default value.", "claude": "OK, defaulting s to ''."},
      {"round": 2, "user": "Even better, throw a TypeError.", "claude": "Right — throwing is the explicit behaviour."}
    ],
    "finding-2": [
      {"round": 1, "user": "Skip — already fixed in commit abc123.", "claude": "Acknowledged, removing this from the queue."}
    ]
  }
}
```

The renderer reads this sidecar (if present) and renders one `<div class="ve-finding-round">` per `(findingId, round)` entry **above** the always-present new-reply textarea.

### 3.5 Orchestrator (the loop)

A new slash command `/visual-explainer:interactive-report` accepts an agent report path, runs the renderer, opens the page via the existing `share-page` infrastructure, waits for the submit, then:

1. Reads the submit JSON from `ve-select.py` output.
2. For each `finding-reply` entry, calls Claude (sub-agent or main) to generate a per-finding response — the prompt scopes to the original finding text + the conversation history for that finding.
3. Appends `{round: N, user: text, claude: response}` to `replies.json[findingId]`.
4. Re-runs the renderer.
5. Re-opens the HTML.
6. Loop continues until the user clicks Exit (no replies left to address) or closes the window.

For v1, the orchestrator step is **manual** — the user invokes the slash command after each round. v2 can automate the loop with a watch-mode that re-runs the renderer on each `replies.json` update.

## 6. v2 — modal comment threads with live in-place reply

After shipping v1, the user gave a refined spec for the interaction model.

### 6.1 Original v2 user spec (verbatim)

> remember the iter:
> - each point/row/paragraph is market with an hidden id to let claude recognize the thing the user is referring to without having to read it again (waste of tokens). But if claude never read it before, then the id must still be accompanied by the point/row/paragraph that the user will comment later (see below)
> - user selects one point/row/paragraph
> - for selected points/rows/paragraphs the mouse hovering on them displays an option "comment this"
> - the user click on "comment this"
> - an input box is added on the right of the point/row/paragraph, with indication to "write your comment here..", modal (cannot interact with anything else except that). The box has a SEND and CANCEL buttons. the box MUST NOT COVER THE TEXT OF THE REPORT IN ANY WAY! scroll more to the right if needed, add a column to the table or add a space wrapping the text, but let the box never overlap or hide the text.
> - the user will write his comment into the box and press SEND (or cancel to dismiss the floating box)
> - claude receive the comments with the hidden id of the point/row/paragraph (and only if cladde has never read the content of the document with the ids, then the point/row/paragraph content is fully shown to claude)
> - claude answer to the comment of the user via a special tool/skill of the plugin
> - this tool will update the html page without closing it, so the user will only see its comment being sent and after a couple of seconds the claude answer will be printed in the SAME input text box where he wrote the first comment.
> - the user can use a "answer" button to add a followup comment in response to the claude answer. and claude can answer again. the user can stop this choosing DONE button instead of ANSWER button.

### 6.2 Comment-box layout (user sketch)

```
----------------------------------------
|  thread  |                           |
|----------|                           |
| 1:  user |                           |
| 2: agent |                           |
| 3:  user |                           |
| 4: agent |  (text of the message)    |
|>5:  user<|  (becomes an input box    |
|          |   when the user press     |
|          |   ANSWER)                 |
|          |                           |
|          |                           | <--- vertical scrollbar if content overflows
|          |                           |
|          |                           |
|--------------------------------------|
|    [ANSWER]           [DONE]         |
----------------------------------------
```

Two columns inside the box:
- **Left** — clickable thread index. One row per turn (`N: user` or `N: agent`). The active turn is highlighted with `>` markers and a stronger background tint.
- **Right** — content of the active turn. When the active turn is the next-to-be-composed user turn, the right pane is an editable textarea; otherwise it's static rendered text.
- **Bottom** — `[ANSWER]` (submit the active textarea text and start the next round) and `[DONE]` (close the modal).

### 6.3 Hidden-ID model

Every commentable element in the rendered HTML carries a `data-ve-comment-id="<8-char-hex>"`. The id is computed from a deterministic hash of the element's normalised text content (whitespace-collapsed, first 200 chars), so the same paragraph in the same report always gets the same id across re-renders (and the user's prior comments stay anchored).

The renderer also emits a sidecar **`<report>.idmap.json`** that maps every `commentId` → `{kind, text, sectionId}`. The orchestrator consults this when an unknown id arrives in a comment payload — the id alone is enough for "Claude already saw this" rounds, but the orchestrator can dereference to the full text on demand.

### 6.4 Hover affordance

On `mouseenter` of any `[data-ve-comment-id]`, the runtime injects a tiny "💬 Comment this" pill in the top-right corner of the element (absolute-positioned over the element's first row). On `mouseleave` the pill fades out. Click on the pill opens the modal anchored to that element.

The pill is intentionally small (16 px tall, 24 px-text wide) so it never disrupts the visual flow of the report itself.

### 6.5 Reflow vs overlay

The modal is **never allowed to overlap report text**. Implementation:

- The modal is `position: fixed; right: 0; top: 0; height: 100vh; width: 460px`.
- When the modal opens, the runtime adds `body[data-ve-comment-modal-open="1"]` and a CSS rule that pushes `main { margin-right: 460px; max-width: calc(86ch - 0px); }`.
- Long table rows that would still overflow horizontally get a `scroll-snap-type: x` so the user can side-scroll without losing the modal anchor.

The page becomes inert (`pointer-events: none`) **except** the modal itself and the active commentable element. ESC closes the modal (same as DONE).

### 6.6 Transport — file-based polling

A new pair of HTTP endpoints in `scripts/ve-select.py`:

- `POST /__ve-comment {threadId, commentId, sourcePath, comment}` — appends to `<project>/.ve-comments/<threadId>.jsonl` (one JSON per turn). Returns `{threadId, queued: true}`. Idempotent — re-POSTing the same `{threadId, turn}` does not double-write.
- `GET /__ve-reply/<threadId>?since=<turn>` — returns 204 if no new turns are available, else 200 with `{turn, role:"agent", text}`. The page polls this every 1.5 s after each ANSWER.

Reply files are written to `<project>/.ve-comments/<threadId>.reply.<turn>.json` by the orchestrator slash command. The runner just serves whatever is on disk.

### 6.7 Orchestrator — `/visual-explainer:respond-to-comment`

A new slash command:

- `--queue-dir <path>` (default: `<project>/.ve-comments`).
- Reads every `.jsonl` file with at least one un-replied user turn.
- For each, looks up the source doc's `idmap.json`. If the `commentId` is unknown (Claude has never read the doc), it inlines the full text from `<report>.md`. Otherwise just passes the id.
- Generates a per-comment reply scoped to the thread + the source-doc context.
- Writes `<threadId>.reply.<turn>.json` with `{turn, role:"agent", text}`.
- `--watch` mode loops every 2 s, picking up new turns as they arrive.
